# Item ownership and persistence audit of `codex/master-stable`

Audited commit: `72238a8f594e0841fab7e7a5c6b27e22a57f92dd`. Audit date: 23 September 2026. The checkout was clean before this report. There is no local ref named exactly `master-stable`; `codex/master-stable` tracks `origin/codex/master-stable`.

## Executive finding

The repository has a sound central custody transaction, but it is not the universal entry point for item mutation. Normal get, put, drop, give, shop, auction, pet, collector, corpse, and some staff paths use operation IDs, expected revisions, ledger rows, and post-commit publication. Older gameplay, spells, scripts, damage, decay, and crafting still mutate or free live objects directly. The low-level object helpers do not enforce the custody boundary. Consequently, an active item can disappear, move to another room or container, or change hands while `item_current_owner` still describes its old state. Complete player saves detect much of this drift and refuse to replace item rows; that protects the durable record but can make a visible gameplay action fail to persist.

This is a source audit. I did not run a live database or gameplay server. For dynamic special procedures, the finding is conditional on an affected object having an active generic custody row. A UID or `ITEM_TRANSIENT` flag alone is not proof of active custody; the runtime lookup is the decisive check. This report inventories the transition families and all concrete bypass families found in the audited source. It does not claim that every individual call to a low-level helper is unsafe: many operate on newly allocated props, money, or player corpse roots.

## The intended invariant

`item_current_owner` is the custody authority, including `root_item_uid` and `parent_item_uid`; `item_ownership_ledger` is its immutable history. The generic transfer validates the expected owner, owner revisions, item revisions, state, vnum, full selected subtree, and target parent; then it updates current rows, ledger, revisions, and relevant materialized item payloads in one critical transaction. See [`item_transfer_repository.c`](../../src/item/item_transfer_repository.c) and the documented rule in [`DATABASE.md`](../reference/DATABASE.md). Same-owner reparenting still needs a transfer.

The game-thread adapter captures the object forest and item blob, submits an operation ID, and applies the runtime registry and live movement after an acknowledged commit. Its publication-aware path retains failed publication and its fence for retry. See [`item_movement_transaction.c`](../../src/item/item_movement_transaction.c). The flatfile repository implements the same typed ownership model for its supported domains. Player complete-save verification compares the snapshot against all active player custody rows before deleting any saved item rows; [`player_snapshot_repository.c`](../../src/player/player_snapshot_repository.c) is a guard, not a substitute for a transfer.

The relevant predicate is [`item_command_uses_durable_ownership()`](../../src/item/item_command_policy.c): nontransient generic items use the durable path, and a transient item also uses it when it has an active runtime ownership row. Money and player corpse roots have separate lifecycle paths.

### Direct comparison

| Required effect | Handled example | Bypass example | Shared fix |
| --- | --- | --- | --- |
| Retire a consumed or destroyed UID before freeing it | Key break and staff destroy submit a destruction reason | Junk, potions, ingredients, lockpicks, device scrolls, and decay call `extract_obj()` | One destruction intent that selects the entire affected subtree, commits custody and associated reward/cost, then publishes removal. |
| Reparent or change owner before moving the live object | Get, put, give, trusted steal, and forced weapon drop submit expected topology | Donation, spell drops, scripts, and direct resurrection cleanup use `obj_from_*`/`obj_to_*` | Route every active UID movement through the same planner, including same-owner parent changes and room moves. |
| Keep outputs and inputs atomic | Shop trade and corpse lifecycle commit item and domain state together | Salvage, crafting, alchemy, and encrusting separately destroy inputs and grant an output | Composite multi-item effect with one operation ID and deterministic locks. |
| Complete the live effect after durable commit | Creation grant and opt-in `bool` publication callbacks retain a failed publication fence | Normal get/put/drop/give callbacks and shop/auction publication can discard the retry handle | Common publication result contract, UID-based continuation, and retained replay/reload work. |
| Persist an in-place payload edit | Snapshot serialization captures fields when a guarded full save occurs | Repair, enhancement, condition damage, and effect setters change fields without a uniform item dirty signal | Explicit payload update intent or dirty API tied to the authoritative owner projection. |

### Additional conditional sites and deliberately excluded sites

The same predicate must be applied to direct extraction in [`necromancy.c`](../../src/classes/necromancy.c) (corpse and ingredient spells, including lines 1705 and 3381–3447), [`drannak.c`](../../src/classes/drannak.c) (orb and reward paths, lines 347–392), [`disguise.c`](../../src/classes/disguise.c) (kit use, lines 286 and 371), [`sillusionist.c`](../../src/classes/sillusionist.c) (line 1753), [`epic_skills.c`](../../src/classes/epic_skills.c) (line 1312), [`tradeskill.c`](../../src/economy/tradeskill.c) (bandage and other inputs, lines 1109–1309 and 2487–2542), [`crafting.c`](../../src/economy/crafting.c) (all raw inputs throughout lines 291–1538), [`mining.c`](../../src/economy/mining.c) (lines 283, 360, 909), and [`specs.room.c`](../../src/specs/specs.room.c) (sacrifice/food/room procedures at lines 699, 729, 1192). Some of these consume player-carried inputs; others operate on NPC stock, room props, or objects created only for the action. A blanket safe/unsafe verdict by filename would be misleading. The proposed boundary would make the distinction at runtime.

World and account systems also call `extract_obj()` directly: [`nexus_stones.c`](../../src/economy/nexus_stones.c), [`kingdom_harvest.c`](../../src/kingdom/kingdom_harvest.c), [`kingdom_craft.c`](../../src/kingdom/kingdom_craft.c), [`guild/artifact.c`](../../src/guild/artifact.c), [`auction_houses.c`](../../src/economy/auction_houses.c), [`account_reward.c`](../../src/account/account_reward.c), [`world_recovery_pipeline.c`](../../src/world/world_recovery_pipeline.c), and numerous zone special procedures. Many are temporary probes, cleanup after a committed operation, or different domain lifecycles. They are not proved safe by that context alone; the architecture currently provides no universal assertion that a selected UID lacks an active generic row. Artifact extraction additionally changes its specialized artifact register and must be coordinated with generic custody if the artifact is adopted.

There are important safe raw extractions: failed `read_object()` probes before adoption (for example `shop.c:215–274`, `salchemist.c:1476–1486`), creation-grant submission failures (`ethermancer.c:592–599`), post-commit publication under a verified operation (for example shop invalid-stock cleanup at `shop.c:370–376` and managed key break at `actmove.c:75–126`), and known money/world effects outside generic custody. These demonstrate that replacing every textual `extract_obj()` with a database call would be incorrect.

### Why the existing guards do not close these gaps

* [`obj_to_char()`](../../src/world/handler.c) checks that an active row names the destination player or admits a detached creation candidate. This protects one inbound player edge only. It checks owner, not parent/root topology, and `obj_from_char()`, `obj_to_obj()`, `obj_to_room()`, and `extract_obj()` do not perform equivalent transfer admission.
* Low-level dirty marks request a later snapshot. They do not change `item_current_owner` or append a ledger event. The complete-save custody guard then rejects the mismatched snapshot instead of making the mutation durable.
* `ITEM_TRANSIENT` describes decay behavior, not guaranteed absence from ownership. The policy explicitly treats an active transient UID as durable.
* `gone_for_good` in `extract_obj()` controls artifact bookkeeping; it is not a custody destruction operation.

## Recommended refactor

Keep the proven transfer repository and critical-command coordinator. Add one typed **item change boundary** above them, and reserve raw `obj_*` helpers for applying an already committed result or manipulating objects proven outside durable custody.

1. Introduce `item_change_request` with explicit operations: `create`, `move`, `reparent`, `destroy_subtree`, `destroy_root_release_children`, `consume_and_create`, and `update_payload`. Each request identifies UIDs, source owner, destination owner/parent, expected revisions, reason, and an operation ID. Runtime classification uses the active ownership row, not item flags.
2. Have a single planner capture and validate the exact forest, derive affected owner domains, and choose the existing generic transfer or a domain composite command. Keep money, player corpses, shops, auctions, and collector rules in their current domain modules; they share a common commit/publication contract rather than a giant switch in `handler.c`.
3. Add a multi-root, multi-effect composite command for crafting, salvage, enhance, and decay-with-child-release. It must lock all affected owners/items in deterministic order and commit every destruction, creation, wallet change, ledger row, payload, and outbox event under one operation ID. A chain of individual transfers would still allow partial recipes.
4. Publish only after durable acknowledgement. Store UID-based continuation data, re-resolve live objects, validate topology, and retain committed-but-unpublished work and fences until replay/reload or explicit repair. Apply this to shop/auction publication as well as generic item movement.
5. Put a guard at `obj_from_*`, `obj_to_*`, `equip/unequip`, `extract_obj`, and direct serializable-field mutation boundaries. During migration, emit structured diagnostics for active UID mutations outside a committed-publication scope; then fail closed once callers are converted. The scope must be a narrow internal capability issued by the publication coordinator, not a public boolean that arbitrary callers can set.
6. Convert highest-risk consumers first: junk/donate; potion/scroll/key/poison; salvage/crafting/enhance; decay/scrap; forced spell/combat drops; scripted room and mobile movements. Route item metadata changes through a small `item_mark_payload_dirty()` API and verify durable owner payload updates for room, corpse, locker, and shop domains.

The core abstraction is an **intent plus committed publication**, with policy outside the low-level linked-list mechanics. This is smaller and safer than making every `obj_to_*` call synchronously write SQL: those helpers run during loading, world generation, and temporary object construction and cannot wait for asynchronous commit.

## Verification and remaining proof

I searched the C/C++ source for the movement/extraction primitives, transfer submission, ownership runtime access, and item persistence writes; inspected the central authority, snapshot guard, load path, primary commands, lifecycle/economic modules, and representative special procedures. The scan found about 1,700 textual occurrences of the nine low-level movement/extraction names, including definitions/comments and known safe publication sites, so a raw occurrence count is not a defect count.

Read-only focused checks on this Windows checkout:

* `python tests/async/test_live_item_movement_contract.py`: 15 tests passed.
* `python tests/async/test_player_item_custody_write_guard.py`: passed.
* `python tests/async/test_item_ownership_contract.py`: 6 of 7 passed; the remaining assertion inspects Unix executable permission bits on migration scripts and fails on this Windows filesystem. It does not exercise an ownership behavior.

Before implementing, add behavior tests for each conversion: commit rejection leaves live topology and rewards unchanged; successful destruction retires every selected UID; same-owner reparent increments ledger revisions; composite recipes commit all inputs and output together; post-commit publication failure remains fenced and replayable; a complete save and reload preserve the result. Run both SQL and flatfile variants and inspect `reconcile_item_ownership.sh` after isolated journeys. No production migration or reconciliation write was run for this audit.
