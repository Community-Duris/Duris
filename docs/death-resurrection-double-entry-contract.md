# Death/resurrection double-entry integration contract

**Scope:** a real PC's ordinary death, corpse wallet/item custody, and resurrection. This excludes mob and pet raising.

## Existing event path that the journey exercises

1. `src/combat/fight.c::make_corpse()` calls `money_to_inventory()` for a player, then `submit_next_corpse_item()` transfers carried/equipped durable roots into the corpse. `src/world/handler.c::money_to_inventory()` submits a wallet-to-coin-pile composite (`currency_transaction_coin_wallet()` plus an item-creation transfer) and commits its two endpoints through the coin/currency command path. The newly created pile then moves from player to corpse and, during resurrection, to destruction while its value returns to the wallet. The observable records are `currency_ledger` and `item_ownership_ledger`; these are domain journals, not double-entry accounting operations.
2. The corpse-root custody path records per-item `item_ownership_ledger` events (`item_transfer_reason::corpse_create`, reason 9) through `src/item/item_transfer_repository.c`. The pile also emits `creation` (reason 2), `corpse_create` (reason 9), and `destruction` (reason 3). Current source has no writer/caller for `economic_accounting_item_reference` on these paths.
3. `src/magic/magic.c::spell_resurrect()` delegates to `persistence_defer_corpse_resurrection()` in durable corpse mode. `src/world/handler.c::continue_corpse_resurrection()` first drops any remaining live player-owned items to the old room, then submits `corpse_lifecycle_transaction_resurrect()`. The SQL lifecycle path updates corpse custody and wallet state; the observable reasons are `item_transfer_reason::corpse_loot` (reason 11) and `currency_reason_type::corpse_lifecycle` (reason 18). The legacy fallback in `spell_resurrect()` directly mutates wallet/object/room state and calls `writeCharacter()`.
4. `src/persistence/critical_command_repository.c` invokes `economic_sql_bank_transaction` only for an `account_bank` command accepted by `accounted_bank_envelope()`. Death's coin-transfer, corpse item-transfer, and corpse-lifecycle commands do not use that bank-only accounting writer. The SQL contract test verifies the resulting evidence, rather than treating the legacy ledgers as accounting proof.

## Required integration for each successful death/resurrection journey

- Preserve the existing critical operation IDs and authoritative `currency_ledger` / `item_ownership_ledger` rows. For every death or resurrection item event, write exactly one matching `economic_accounting_item_reference` whose legacy key is `(operation_id, event_index, item_uid, after_revision)`. Link it to the economic root and child index that own the operation; never create an unlinked/second item event to satisfy accounting.
- For every wallet value change in the composite coin conversion and corpse resurrection, link the currency event to an economic root/child and post at least two coin legs with net `SUM(copper_value) = 0`. Preserve denomination totals and revisions: wallet clearing plus pile creation must reconcile within the death composite, while pile consumption plus restored wallet must reconcile within the later resurrection operation.
- Keep each *individual* critical mutation and its accounting evidence in one commit boundary: the death wallet/pile composite, corpse-create item transfer batches, and the later resurrection lifecycle are distinct operations. Link them through durable corpse identity/lineage, not a fictitious transaction spanning death and resurrection. Include any resurrection pre-claim `player -> old room` drops. A replay or rejected operation must not publish live ownership/wallet changes or orphan accounting evidence.
- The integration must cover both the durable SQL path and the legacy/non-durable spell fallback before claiming the full death/resurrection goal. The executable RED journey at `tests/async/test_death_resurrection_mysql_journey.py` exercises the durable SQL path only.

**Observed RED (disposable SQL, 2026-09-25):** The real-PC journey reached death, corpse persistence, a real `cast 'resurrect' corpse`, restored wallet and all 12 original item UIDs, and consumed the newly created coin pile. It found 12 corpse-create plus 12 corpse-loot events for those items, and one each of coin-pile creation, corpse move, and destruction. All 27 item events lack accounting item references; both currency-ledger operations lack an accounting root/child and thus balanced-posting proof. Raw run: `/opt/data/workspaces/duris-persistence-tools/logs/20260925T070452Z-red-death-resurrection-journey.log`.

The current code provides currency/item domain journals and a bank-only economic accounting integration. It does not prove a shared-root owner/API for these non-bank writers, so this contract records the required seam without adding a speculative production change.
